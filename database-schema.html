设计原则

先保证事实可追溯、权限可收敛，再谈性能与扩展。

01单一事实源

PostgreSQL 存业务事实；Redis 只做缓存、限流和队列 broker；文件二进制放私有对象存储，库里只留对象 key 与哈希。

02约束先于代码

状态用 varchar + CHECK 管理，避免 PostgreSQL enum 难以演进；NOT NULL、UNIQUE、FK 尽量落库，应用层只做提示性校验。

03权限随数据走

files、doc_chunks、ai_citations 冗余 case_id。检索必须先按 case_id 权限过滤，再计算相似度，禁止先全库召回后筛选。

04AI 全链路留痕

模型、提示词版本、token、成本、引用来源、工具调用与反馈全部落库；流式中断必须能与成功完成区分。

05幂等与顺序

消息用 (conversation_id, seq) 保证严格顺序；client_message_id 与 idempotency_key 唯一约束防止重试造成重复写入或重复扣费。

06JSONB 有边界

JSONB 只存 AI 结构化输出和稀疏元数据；需要过滤、排序、聚合的字段必须落成普通列，必要时建生成列索引。

07向量不急于独立

MVP 用 pgvector + HNSW。embedding 维度在迁移中固定；更换模型时新建列或新表回填，不原地修改维度。

08敏感数据最小化

不存完整身份证号；手机号与证件号只留脱敏字段；对象 key 私有且不下发；审计日志不记录正文和敏感值。

明确不做：EAV 万能属性表、单表存全部业务的 God table、把 Redis 当聊天记录事实源、MVP 阶段引入独立向量库或多 Agent 状态库。

状态字典

英文代码入库，中文文案由前端映射；新增状态必须同步 CHECK 约束与迁移。

cases.analysis_status 案件分析状态

not_analyzed未分析，仪表盘显示 “? 胜诉率”
analyzing分析中，显示进度态
analyzed已分析，展示最新胜诉率结果
failed分析失败，保留失败原因并允许重试

cases.evidence_upload_status 证据上传状态

not_uploaded未上传任何材料
partial部分证据目录项已有材料
completed全部必传材料已上传

evidence_items.status 材料审核状态

ai_analyzingAI 分析中
ai_passedAI 分析通过
ai_failedAI 审核失败，展示失败原因
lawyer_pending律师待审核
lawyer_rejected律师驳回

ai_messages.status 消息生成状态

streaming流式生成中，连接断开后可取消
completed完整生成并已落库
failed生成失败，不计为成功回答
cancelled用户主动取消或超时终止

async_jobs.status 异步任务状态

queued已入队，等待 Worker
running执行中
succeeded成功，业务结果已写回
failed失败，可重试
cancelled已取消
dead超过最大重试次数，转人工排查

tool_calls.status 工具调用状态

pending待执行
running执行中
succeeded成功，result 已落库
failed失败，记录 error_message
cancelled随会话取消
